# 5-17 已平仓收益异常说明

## 一句话结论

这次 BUG 的核心原因是：纸上交易系统在更新持仓价格时，过度信任了 GMGN 返回的 `price`。当 GMGN 对个别 Token 返回了明显错误量级的价格后，系统把这个错误价格当成真实 USD 价格去计算止盈、平仓和收益，最终导致已平仓列表出现几万美金、几十万百分比的离谱收益。

## 发生了什么

已平仓列表里出现了两条异常记录：

- `F.03`
  - 显示收益：`+127617.68%`
  - 显示盈利：`+$35732.95`
- `SPCX`
  - 显示收益：`+50311.51%`
  - 显示盈利：`+$24149.53`

这两个结果都不符合实际 Token 价格走势。

比如 `F.03` 的入场价是 `0.0000610467`，最终平仓价是 `0.00007653`，真实涨幅大约只有 `25%`，不可能赚出三万多美元。

真正的问题是：中途系统曾经记录过一个异常高价，例如 `F.03` 的 `peak_price` 被写成了 `0.1731`。这个价格比真实价格高了几千倍。

## 为什么会发生

可以把系统理解成这样：

1. Worker 每轮扫描市场 Token。
2. 扫描结果主要来自 GMGN。
3. 如果当前有纸上持仓，系统会拿最新价格更新持仓。
4. 持仓更新会判断是否触发止盈、止损、trailing。
5. 如果触发卖出，就把卖出金额和收益写进数据库。

问题出在第 3 步。

旧逻辑里，系统获取持仓最新价格时有两个风险：

- 如果这个 Token 正好出现在当前 GMGN 扫描列表里，系统会直接使用 GMGN 返回的 `token.price`。
- 如果需要额外查询实时价格，旧逻辑也是先用 GMGN，只有 GMGN 没价格时才用 DexScreener。

这意味着：只要 GMGN 返回了一个错误价格，系统就可能直接拿这个价格去更新持仓。

这次异常就是这样发生的。

## 为什么收益会被放大

纸上交易的收益计算本身并不复杂：

```text
卖出金额 = 卖出 Token 数量 × 当前价格
收益 = 卖出金额 - 成本
收益率 = 收益 / 初始仓位金额
```

如果当前价格是真实价格，计算结果就是正常的。

但如果当前价格被错误放大了几百倍、几千倍，那么卖出金额也会被同步放大。

例如：

```text
真实价格：0.00008
异常价格：0.1731
```

系统并不知道这个价格是错的，于是继续按：

```text
卖出 Token 数量 × 0.1731
```

去计算卖出收入。

所以这不是前端展示错了，也不是百分比格式化错了，而是数据库里的已平仓收益已经被错误价格污染了。

## 这次具体污染了哪里

异常价格进入持仓生命周期后，会影响这些字段：

- `current_price`
- `peak_price`
- `close_price`
- `realized_proceeds_usd`
- `realized_pnl_usd`
- `pnl_pct`

对 `SPCX` 来说，异常价格直接成为平仓价格，所以收益一次性被放大。

对 `F.03` 来说，最终平仓价看起来不夸张，但中途的异常峰值价已经触发了 3 档止盈，提前把大额已实现收益写进了数据库。后面 trailing 平仓只是关闭了这条已经被污染的持仓。

## 解决方案

已经做了两个修复。

第一，实时持仓价格优先使用 DexScreener。

DexScreener 的 token endpoint 会返回明确的 `priceUsd`。对于纸上交易的持仓结算来说，我们更需要稳定的 USD 标价，而不是扫描榜单里的临时价格字段。

修改位置：

- `src/modules/signals/server/live-price-snapshot-service.js`

新逻辑：

```text
先查 DexScreener priceUsd
如果 DexScreener 没有价格，再 fallback 到 GMGN price
```

第二，更新持仓时优先使用实时价格源。

旧逻辑中，如果持仓 Token 正好也在当前扫描列表里，系统会直接使用扫描列表里的 GMGN price。

现在改成：

```text
每轮先给所有 open positions 拉实时价格
如果实时价格存在，优先使用实时价格
只有实时价格缺失时，才使用扫描列表里的 token.price
```

修改位置：

- `src/modules/signals/server/paper-position-lifecycle-service.js`

## 修复后能避免什么

修复后，后续打开中的持仓不会再优先信任 GMGN 的扫描价格。

这样即使 GMGN 偶尔返回异常价格，也更不容易直接污染：

- 止盈判断
- trailing 判断
- 平仓价格
- 已实现收益
- 已平仓收益率

## 已有异常数据怎么办

这次修复只能防止后续数据继续被污染，不能自动修复已经写进数据库的 closed positions。

原因是这两条记录已经把异常价格计算后的结果写进了数据库。

后续可以选一种方式处理：

1. 报表层临时排除这两条异常 closed positions。
2. 手动修正这两条记录的收益字段。
3. 如果能拿到可靠历史价格，就按真实价格重新计算这两笔纸上交易。

这三种方式里，最稳妥的是先在统计里标记或排除异常记录，再单独做一次历史数据修正。
